# 全站真实数据治理模板

## 文档定位
- 目的：为 `T-005 ~ T-019` 提供一套固定的“先定规则，再分波次迭代页面”的执行模板，避免每个页面重复定义字段、状态、口径、核账方式。
- 适用范围：所有正式页面、正式接口、正式写操作、正式聚合逻辑；不适用于纯视觉装饰模块、实验页、开发调试页。
- 生效原则：后续页面任务默认遵循本模板；若页面域存在偏离，必须在对应任务文档中记录“偏离项 + 原因 + 替代规则 + 验证方式”。

## 核心思想
- 不是从页面开始修，而是从业务对象和真实写入事件开始治理。
- 不是只看数据表，也不是只看页面字段，而是做双向闭环：
  - 正向：业务对象/事件 -> 权威表 -> 聚合规则 -> Action/API -> 页面字段
  - 反向：页面展示/动作 -> Action/API -> 查询/写入 -> 表/上游服务 -> 可复算结果
- 每一轮页面迭代都必须复用同一套规则、同一套产物、同一套验收证据格式。

## 强制原则
1. 单字段单口径：同一业务字段在全站只能有一种定义。
2. 原始值优先：服务端返回可核账原始值，格式化放在 UI 层完成。
3. 真数据优先：正式页面字段必须来自真实数据库、真实上游服务或可复算聚合；禁止 mock 兜底。
4. 空态优先于假态：后端未完成、无数据或无权限时，显示空态、禁用态或明确错误，不允许假成功。
5. 读写分离：读接口默认无副作用；需要补数据、刷新状态、补偿修复时必须显式建独立入口。
6. 写操作可回放：创建、提交、领取、支付、评论、保存都要可核账、可重试、可识别重复提交。
7. 页面与数据库双向可追踪：页面字段能追到表，表变化能追到页面动作。

## 固定治理流程

### Phase 0：定义业务对象与关键事件
- 先定义页面域涉及的业务对象，例如：用户、练习会话、逐题记录、课程进度、任务、奖励、排行榜、帖子、支付单。
- 再定义改变这些对象的关键事件，例如：开始练习、提交答案、完成课程、领取奖励、保存设置、发起支付、webhook 回调。
- 每个事件都要回答四个问题：
  - 谁触发
  - 写入哪里
  - 哪些字段改变
  - 是否允许重复触发

### Phase 1：确认权威数据源
- 每个页面字段只能对应一个权威来源。
- 权威来源优先级固定如下：
  1. 权威写表 / 权威上游服务
  2. 可复算聚合
  3. 物化缓存 / 冗余字段
  4. UI 空态 / 禁用态
- 强制规则：
  - 若字段来自冗余列，必须能由权威源复算。
  - 若字段无法映射到数据库或上游服务，不能继续正式展示。

### Phase 2：检查表结构与约束是否支撑真实化
- 先检查模型是否满足真实业务，而不是先写页面兼容脆弱结构。
- 每个核心表至少检查以下项目：
  - 主键、外键、唯一键是否齐全
  - 是否存在支撑幂等的业务唯一键
  - 是否有明确状态字段
  - 是否有 `createdAt` / `updatedAt`
  - 是否能区分“当前值”和“历史事件”
  - 是否存在会导致重复写入、重复发奖、重复扣费的结构缺口
- 若表结构不满足要求，先补 schema / 约束，再推进页面接线。

### Phase 3：定义状态机与业务规则
- 每个对象先定义状态机，再写页面逻辑。
- 页面数据状态统一为：
  - `loading`
  - `ready`
  - `empty`
  - `forbidden`
  - `error`
  - `disabled`
- 写操作状态统一为：
  - `idle`
  - `submitting`
  - `success`
  - `failed`
  - `duplicate`
- 奖励/任务类状态统一语义：
  - `IN_PROGRESS`
  - `COMPLETED`
  - `CLAIMED`
- 明确以下规则后才能开发：
  - streak 何时推进
  - active day 何时成立
  - daily task 何时创建、何时推进、何时可领取
  - leaderboard 何时加分、何时结算
  - webhook / sync / ensure 是否天然幂等

### Phase 4：定义聚合口径与算法
- 所有聚合字段必须先定义公式、过滤条件、时间窗口、空值规则。
- 统一时间窗口定义：
  - 今日：按用户时区自然日；无用户时区时默认 `Asia/Kuala_Lumpur`
  - `7D`：包含今天在内的最近 7 个自然日
  - `30D`：包含今天在内的最近 30 个自然日
  - 最近记录：默认最近 3 条，页面如有例外需显式写明
  - 活跃日：当天存在有效学习事件才算，不以单纯打开页面为准
- 有效学习事件必须显式定义，至少包括：
  - 完成练习提交
  - 完成考试提交
  - 完成课程/lesson
  - 完成任务推进
- 禁止项：
  - 禁止把访问 Dashboard 计为活跃日
  - 禁止把页面加载作为 streak 刷新触发条件
  - 禁止同一字段在不同页面使用不同公式

### Phase 5：建立字段字典

#### 通用字段定义
| 字段 | 类型 | 统一定义 | 存储/返回要求 | UI 规则 |
|---|---|---|---|---|
| `score` | `number` | 单次练习/考试得分百分比 | 整数 `0-100` | UI 显示 `85%` |
| `accuracy` | `number` | 正确数 / 总作答数 * 100 | 整数 `0-100` | 不返回字符串百分号 |
| `progress` | `number` | 当前对象完成进度百分比 | 整数 `0-100` | UI 负责进度条映射 |
| `masteryLevel` | `number` | 掌握度百分比 | 整数 `0-100` | 若有等级文案，由 UI 二次映射 |
| `studyTimeSeconds` | `number` | 学习时长原始秒数 | 服务端返回秒数 | UI 再格式化为 `xh ym` |
| `durationSeconds` | `number` | 单次会话/动作耗时秒数 | 服务端返回秒数 | 不在服务端拼接“分钟” |
| `questionsCount` | `number` | 题目数量或作答数量 | 非负整数 | 命名显式带 `Count` |
| `mistakesCount` | `number` | 错误作答次数 | 非负整数 | 去重错题数必须另起字段名 |
| `streakDays` | `number` | 连续有效学习日天数 | 非负整数 | 不复用为登录天数 |
| `xp` | `number` | 当前经验值总量 | 非负整数 | 等级由规则映射 |
| `level` | `number` | 基于 XP 规则计算出的当前等级 | 正整数 | 计算规则必须统一 |
| `rank` | `number \| null` | 榜单 1-based 排名 | 正整数或 `null` | `null` 表示未上榜 |
| `activeDays` | `number` | 窗口内有有效学习事件的自然日数量 | 非负整数 | 不混用登录日与学习日 |
| `createdAt` / `updatedAt` | `Date` 或 `ISO string` | 创建/更新时间 | 接口层统一一种序列化方式 | 相对时间展示由 UI 处理 |

#### 语义冲突禁止项
- 禁止把 `mistakesCount` 当成“去重错题本数量”。
- 禁止把 `score` 和 `accuracy` 混用。
- 禁止把 `progress` 当作“掌握度”。
- 禁止在服务端返回 `studyTime: "1.5h"` 这类展示字符串。

#### 页面聚合字段命名规范
| 场景 | 正确命名 | 禁止命名 |
|---|---|---|
| 总览汇总 | `dashboardStats`, `overviewStats`, `practiceSummary` | `data`, `info`, `resultData` |
| 列表分解 | `subjectBreakdown`, `recentPracticeItems` | `listData`, `itemsData` |
| 趋势数据 | `dailyActivitySeries`, `scoreTrendSeries` | `chartData` |
| 空态计数 | `totalCount`, `completedCount`, `pendingCount` | `count1`, `count2` |

### Phase 6：建立页面映射矩阵
- 每个页面都必须产出字段映射矩阵，格式固定如下：

| 页面字段 | 页面组件 | Action/API | 数据表/服务 | 计算公式/过滤条件 | 空态/异常态 | 核账方式 |
|---|---|---|---|---|---|---|
| 示例：`accuracy` | Dashboard 顶部卡片 | `getDashboardStats` | `user_attempts` | `correct / total * 100` | 无数据返回 `0` + 空态文案 | SQL + 页面截图 |

- 每个 CTA / 跳转 / 交互都必须在矩阵中有归属，不允许“页面有入口，但后端无真实能力”。

### Phase 7：定义 Action / API 契约
- 所有关键读写接口必须固定说明：
  - 输入校验
  - 成功输出结构
  - 失败输出结构
  - 权限校验
  - 幂等策略
  - 并发策略
- 强制规则：
  - `get*` / 查询接口默认不得有写副作用
  - `ensure*` / `sync*` / webhook / 奖励领取必须显式定义幂等键
  - 重复提交必须能返回 `duplicate` 或等价安全结果

### Phase 8：按页面族迭代实现
- 页面族一律按同一模板推进：
  - `.1` 盘点路由、页面、组件、CTA、当前数据源
  - `.2` 建立字段映射与权威数据源矩阵
  - `.3` 对齐读接口 / Server Action / 聚合逻辑
  - `.4` 对齐写接口 / 提交动作 / 权限与幂等
  - `.5` 清理 mock / fallback / 假成功，补空态、错误态、禁用态
  - `.6` 完成本页面族验证：页面冒烟、字段核账、重复提交/刷新验证
- 实施顺序固定：
  1. 先写规则与映射
  2. 再补 schema / 约束缺口
  3. 再改 Action / API / 聚合
  4. 再接页面字段
  5. 再清 mock 和假成功
  6. 最后做核账与回归

## 关键门禁清单

### Schema 门禁
- 关键表存在支撑幂等的唯一键或等价防重机制
- 关键关系具备外键或等价引用约束
- 关键事件可追踪到时间点与触发者

### 逻辑门禁
- 读接口不偷偷写库
- 写接口重复调用不会重复副作用
- 冗余字段都能由权威源复算

### 页面门禁
- 没有 mock / fake / preview-only 正式展示
- 缺能力时用空态、禁用态、错误态，不伪装可用
- 页面值能对到 SQL 或上游返回

## 写操作核账模板
- 每个关键写操作至少保留以下证据：
  1. 触发前页面状态
  2. 请求输入摘要
  3. 数据库/上游执行前快照
  4. 数据库/上游执行后快照
  5. 页面成功/失败反馈截图
  6. 重复提交再次执行结果

## 页面域验收模板
- 每个页面域至少要覆盖：
  - 成功场景
  - 无数据场景
  - 无权限场景
  - 异常场景
  - 重复提交/刷新场景
- 证据形式固定为：
  - 页面截图
  - SQL 或后台快照
  - API 返回样例
  - 关键日志摘录

## 非核账展示模块处理规则
- 纯装饰性模块可以不纳入字段级核账，但必须在页面任务中标注“非核账展示模块”。
- 这类模块不得冒充真实业务数据，不得使用会误导用户判断的伪统计、伪榜单、伪奖励。
- 如 `DailyInspiration` 这类模块保留，应明确标注为内容/装饰模块，而非业务统计模块。

## 模板完成判定（DoD）
- 已定义业务对象、关键事件、权威数据源、表结构门禁、状态机、聚合口径、字段字典、页面任务模板。
- 后续页面域任务可以直接套用本模板推进，而无需重新发明一套规则。
- 任一页面字段都能回答以下问题：
  - 它是什么
  - 它从哪来
  - 它怎么算
  - 它何时变化
  - 它如何核账
  - 它无数据时显示什么
