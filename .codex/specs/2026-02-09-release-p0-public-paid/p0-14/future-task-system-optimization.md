# P0-14 未来优化记录：任务系统与任务池演进建议

## 背景

本记录用于沉淀 MVP 闭环后需要回头处理的任务系统优化项。  
触发背景来自 Dashboard `T-005.14` 对 `dailyTasks` 链路的收口：当前系统已经能稳定支持首页展示、任务推进、onboarding 完成与奖励领取，但整体仍属于“可上线的硬编码实现”，并不适合长期扩张。

当前相关实现主要分布于：

- `src/lib/gamification/config.ts`
- `src/actions/gamification/daily-tasks.ts`
- `src/actions/gamification/achievement.ts`
- `src/components/dashboard/DailyMissions.tsx`

## 当前实现现状

### 1. 当前系统偏硬编码

当前任务系统的三层都偏静态：

- 任务类型：写在 Prisma `DailyTaskType` enum 中
- 默认任务模板：写在 `config.ts`
- 任务分配规则：写在 `daily-tasks.ts`

目前已存在的任务类型包括：

- `LOGIN`
- `COMPLETE_LESSON`
- `FIX_ERROR`
- `QUIZ_SCORE`
- `ONBOARDING_PROFILE`
- `ONBOARDING_GOALS`
- `ONBOARDING_ASSESSMENT`

### 2. 当前实现适合 MVP，但不适合长期扩张

当前结构的优点：

- 简单直接
- 易于快速上线
- 风险面较小
- 对当前 Dashboard 首页闭环足够

当前结构的限制：

- 新任务类型需要改代码甚至改 schema
- 任务模板和奖励值不可后台配置
- 任务投放策略不可按用户分层灵活调整
- 活动任务、实验任务、召回任务难以快速上架
- 文案、奖励、时间窗口都需要发版

## 本轮讨论后的核心判断

### 1. 不是所有任务都应该永久写死

对于当前项目，更合理的做法是区分：

- 固定核心任务
- 运营型任务
- 实验型任务

其中：

- 固定核心任务可以预先设计并长期稳定存在
- 运营型和实验型任务不应长期依赖硬编码

### 2. 任务系统应该拆成“能力层”和“配置层”

建议拆为两层：

#### A. 任务能力层

由代码维护，定义系统“能识别哪些行为”。

例如：

- 登录
- 完成练习
- 完成课程
- 完善资料
- 设置目标
- 完成测评
- 修正错题

这层仍然需要代码实现，因为它涉及：

- 行为事件从哪里产生
- 如何统计
- 如何幂等
- 如何核账

#### B. 任务配置层

由数据库或后台配置维护，定义：

- 给谁发任务
- 发什么任务
- 奖励多少
- 什么时候生效
- 任务文案是什么

目标是做到：

- 新增“任务内容”尽量不改代码
- 新增“任务能力”才改代码

## 推荐的任务分类方式

本轮讨论认为，未来不应只保留“今日任务全部写死”的模式，而应支持按任务大类分配。

建议最少支持以下分类：

### 1. 基础任务

面向新用户或关键行为引导。

例如：

- 完善资料
- 设置学习目标
- 完成首次测评

特征：

- 通常只出现一次
- 更接近 onboarding / activation

### 2. 常规任务

面向日常学习行为。

例如：

- 每日登录
- 完成 1 次练习
- 完成 1 个课程章节

特征：

- 每日 / 每周重复
- 是留存的基础骨架

### 3. 限定任务

面向运营活动或时间窗口任务。

例如：

- 冲刺周完成 1 次模拟考
- 活动期间完成 3 次数学练习

特征：

- 有开始和结束时间
- 需要运营灵活调整

### 4. 成长任务

面向累计成长目标。

例如：

- 累计完成 20 次练习
- 连续学习 7 天

特征：

- 周期更长
- 更接近 quest / achievement，而非纯 daily

### 5. 特殊任务

面向特定人群或定向投放。

例如：

- 召回用户任务
- 某年级专项任务
- 订阅转化任务

特征：

- 需要人群筛选
- 适合做增长或实验

## 后期新增任务应该怎么处理

需要区分两种情况：

### 1. 新增任务模板

例如：

- 完成 2 次练习
- 本周学习 60 分钟
- 完成一次错题整理

如果系统已经具备对应行为事件和统计能力，这类新增不应再要求改代码，应该通过配置完成。

### 2. 新增任务能力

例如：

- 邀请家长绑定
- 完成 AI 讲解互动 3 次
- 发布社区笔记
- 连续 3 天晚间学习

如果现有系统没有事件源、没有统计口径、没有幂等规则，这类新增仍然需要代码改造。

因此，未来任务系统的原则应为：

- 新增任务内容尽量配置化
- 新增行为能力才通过代码扩展

## Admin 端是否需要建设

### 判断结论

短期可以不做完整后台。  
中期应建设轻量任务模板管理界面。  
长期再考虑更复杂的规则引擎与投放系统。

### 什么时候“只改代码”仍可接受

当满足以下条件时，继续靠代码改配置是可以接受的：

- 任务数量少
- 运营改动频率低
- 没有活动编排需求
- 没有人群定向投放
- 没有 A/B 试验需求

### 什么时候必须上 Admin

一旦出现以下需求，后台配置就会变成必要项：

- 运营频繁调整任务
- 奖励值需要快速修改
- 文案需要快速更新
- 需要设置开始/结束时间
- 需要按用户分层投放
- 需要活动任务和实验任务

### 推荐的 Admin 最小可用能力

MVP 之后建议优先建设一个轻量任务模板管理页，仅支持：

- 新增 / 编辑任务模板
- 启用 / 停用
- 配置奖励
- 配置分类
- 配置时间范围
- 配置目标人群

暂不建议一上来就做复杂规则引擎。

## 推荐的未来系统结构

建议未来的任务系统拆成三层：

### 第一层：任务能力层

代码维护，定义系统可识别的行为事件。

例如：

- `LOGIN`
- `PRACTICE_COMPLETE`
- `LESSON_COMPLETE`
- `GOALS_SET`
- `PROFILE_COMPLETED`
- `ASSESSMENT_FINISHED`
- `ERROR_FIX_COMPLETE`

### 第二层：任务模板层

数据库维护，定义任务模板。

建议未来至少支持这些字段：

- `code`
- `name`
- `category`
- `triggerEvent`
- `targetCount`
- `rewardXp`
- `rewardType`
- `startAt`
- `endAt`
- `audience`
- `priority`
- `isRecurring`
- `recurrenceRule`
- `isEnabled`

### 第三层：用户任务实例层

数据库维护，记录某个用户在某一天或某个活动周期内实际拿到的任务实例。

Dashboard 首页展示的应当是这一层，而不是直接展示模板。

## 推荐的任务分配策略

未来不建议所有“今日任务”都固定写死。  
更合理的方式是由分配器按分类和规则组合生成。

建议未来默认组合方式为：

- 固定 1 个基础任务
- 固定 1 到 2 个常规任务
- 如果有活动，则插入 1 个限定任务

这样可以兼顾：

- 新用户引导
- 日常学习留存
- 活动运营灵活性

## 对当前代码的明确结论

### 当前方案可继续支撑 MVP

现阶段不建议因为想做长期架构而打断当前 MVP 闭环。  
当前硬编码任务系统仍然可以继续用于：

- Dashboard 首页闭环
- Achievement MVP 闭环
- 基础任务奖励逻辑闭环

### 但不建议长期继续堆在 `config.ts`

后续如果继续把这些内容都写死在配置文件里，会出现以下问题：

- 任务越来越难维护
- 新需求必须发版
- 运营效率低
- 容易形成前后端逻辑分叉

## MVP 后建议的演进顺序

### 第一阶段

先保留现有行为能力层，新增：

- 任务模板表
- 任务分类字段
- 基础 seed

目标：

- 任务模板从代码迁到数据库
- 现有 Dashboard 展示仍保持稳定

### 第二阶段

建设轻量 Admin 管理页，支持：

- 模板增删改查
- 启停
- 时间范围
- 奖励值
- 分类
- 基础投放对象

### 第三阶段

再考虑更复杂的能力：

- 自动分配规则
- 优先级
- 权重
- 人群筛选
- 活动编排
- A/B 实验

## 后续可拆分的开发主题

MVP 闭环后，可基于本记录拆出独立开发项：

1. 任务系统数据模型重构
2. 任务模板配置化迁移
3. 任务分类与分配器实现
4. Admin 任务模板管理页
5. 活动任务 / 限定任务支持
6. 用户分层投放与实验能力

## 本记录结论

本轮讨论形成的最终结论如下：

- 当前任务系统在 MVP 阶段可接受，但本质上是硬编码方案
- 不建议长期将全部任务类型、模板、奖励与投放规则继续写死在代码中
- 未来应将任务系统拆为“能力层 + 配置层 + 实例层”
- 未来应支持按分类分配任务，而不是只保留固定写死的今日任务
- Admin 端不必立刻重做，但在 MVP 后应进入建设计划
